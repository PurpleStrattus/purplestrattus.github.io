Overview

Beginner is a CTF from Google’s 2020 CTF event. I am doing this CTF as part of my effort to progress as a security researcher. This is the start of my journey as a Junior Security Researcher. I am approaching this with the methodology reflected in the Table of Contents.

I will be running this binary via docker and utilizing binary ninja for static analysis. Dynamic analysis will be done via GDB and potentially other tools.

Security Considerations

The first thing I decided to do was check security settings on the binary, after determining it was an ELF.

Checksec

Pwntools’ Checksec shows Partial RELRO, NX enabled, and PIE enabled.

  • The Arch lets me know that I will be looking at AMD 64 assembly during static analysis. This is also a general consideration for the system this program is designed to run on. Furthermore, this clues me into various considerations, if I were to emulate the program, such as if the program was MIPS.
  • Partial RELRO tells me that the GOT can still be overwritten with the right vulnerability, and it is not set as read-only.
  • Since there is no Stack Canary I won’t have to worry about that if I find an overflow vulnerability.
  • NX means that the stack is non-executable. This lets me know that if I achieve a stack-based overflow, I will not be able to have my shellcode run off of the stack. Instead, I would need to return to somewhere else that is executable and that holds my shellcode.
  • PIE being enabled makes is it so that the program will shift around in memory given that ASLR is typically enabled on hosts. If this was a standalone device, that’d be different. This tells me that any productized exploit will need to ask for the starting address and operate off of known offsets between if so required.
  • Due to the RUNPATH being set to the . directory, replacing libraries with malicious ones would likely be a viable vulnerability. Some form of library hijacking should work.
  • Since the file is not Stripped, static analysis will be easier and potentially more fruitful.

Figuring Out SHUFFLE, ADD32, XOR

  • SHUFFLE Before jumping into Dynamic Analysis if needed, I will attempt to figure out what inputs would survive the operations mentioned above. Below is a table, given the SHUFFLE mask, of the expected placement of each byte after the SHUFFLE.

  • ADD32 Initially this appears to take four 32 byte sections from the data stored. Then, it adds each section of its mask to a four byte section of the string being operated on. If you swap the endianness, the maskef be ad de ad de e1 fe 37 13 37 13 66 74 63 67 becomes 0xDEADBEEF, 0xFEE1DEAD, 0x13371337, 0x67637466.

  • XOR The string will finally be XORed with 78 58 b4 49 8d 1a 5f 38 d4 23 f8 34 eb 86 f9 aa. This will take the string and mask, and compare each bit. Resulting in a new string.

Thoughts

  • The new string gets checked against the original user input, which appears to need to be the same. Is there such thing as a string that doesn’t change even after all those operations? Perhaps it’d be of use to make a Python script that does the conversion automatically.
  • Somehow CTF{ needs to end up being the first 4 bytes of the input string and output? Perhaps CTF{ survives the operations. I can check in GDB or just use a Python script.
  • After doing some googling, I think there’s a way to reverse this using the given masks.
  • There are automated tools like Angr or Z3 that should be able to solve this automatically.
  • Alternatively I could write a script that mimics the exact string transformation. The script would start by iterating through each ascii character (Assuming the flag is in ASCII). It would figure out what index that SHUFFLE would swap the given char to, add the byte from that corresponding index in the add32 mask, and then xor it with the corresponding index in the xor mask. From there, we can see if the value has changed from the original value, or remained the same. If it remained the same, it’s a piece of the puzzle. Maybe. The issue is trying to account for the 32 bit blocks.

Findings

Route to Solution

  • After trying to write a script that manually did all the transformations, I realized that it would be easier to utilize Z3 to solve this issue. So, I decided to dive into Z3 a bit. The stumbling block that I faced was trying to do the ADD32 operation on a single character while accounting for the 32-Bit Block. In hindsight, it may have not been too difficult to perform that operation properly without Z3.
  • The python Z3 library lets you effectively turn bit operations and complex calculations into an equation and then automatically solve it. So, you have to input all the constraints, variables, etc..
  • It has become clear that to find the solution, I must:
    • Take an ASCII character and shuffle it with the SHUFFLE_MASK
    • Place the potential character into a 32 bit block that allows for overflow (Python variables don’t normally allow for overflow)
    • Perform the ADD32 operation on the 32 bit block utilizing the corresponding 32 bit block out of the 4 that are provided in the binary
    • XOR the character with the value in the corresponding place in the XOR_MASK (Ima just call it a mask)
    • Check to see if the value of the ASCII character has changed from the original
  • The flag starts with CTF{ and ends with \0.

Exploitation

Below is the finished Z3 script broken down an explained in detail.

Solve Script Breakdown

  • The first part of the script imports the things we are going to use from Z3. As we go along, I will explain what each import is. It’s important to note, that Z3 keeps tracks of operations involving its own library and datatypes. Z3 will track all the math and operations we are doing with its objects and store them. 
    • from z3 import BitVec, BitVecVal, Concat, Extract, Solver, Or, sat

MAX_FLAG_LEN = 16
CHUNK_SIZE= 4
XOR_MASK = [0x76, 0x58, 0xb4, 0x49, 0x8d, 0x1a, 0x5f, 0x38, 0xd4, 0x23, 0xf8, 0x34, 0xeb, 0x86, 0xf9, 0xaa]
ADD32_VALUES = [0xef, 0xbe, 0xad, 0xde, 0xad, 0xde, 0xe1, 0xfe, 0x37, 0x13, 0x37, 0x13, 0x66, 0x74, 0x63, 0x67]
SHUFFLE_MASK = [0x02, 0x06, 0x07, 0x01, 0x05, 0x0b, 0x09, 0x0e, 0x03, 0x0f, 0x04, 0x08, 0x0a, 0x0c, 0x0d, 0x00]

def solver_builder():
    beginner_flag = [BitVec(f"f{i}", 8) for i in range(MAX_FLAG_LEN)]
    beginner_solver = Solver()
  • Starting out, we are creating a variable (beginner_flag) that will hold/represent our flag. BitVec(f"f{i}", 8) specifies that a custom Z3 datatype known as a BitVec will be created. A BitVec is a fixed size integer that will wrap when overflowed. The arguments we pass to the function determine the name and fixed size of the BitVec variable that we create. In this case, we create a variable with a formatted naming pattern and an 8-bit size. Then we loop through this function call MAX_FLAG_LEN times, which is 16. At the end, beginner_flag will hold 16 8-bit BitVec integers in a list, representing each character of our flag.
    • beginner_flag = [f0, f1, f2, f3, f4, f5, f6, f7, f8, f9, f10, f11, f12, f13, f14, f15].
    • beginner_solver = Solver() is just creating an instance of the solver object that will hold all our constraints and rules for the mathematical operation we do. So when we come up with rules or constraints, we will have to .add() them to beginner_solver.

  • The following code will go through four 32-bit chunks, iterate through all 16 characters, perform the SHUFFLE operations, perform ADD32 operations on each chunk, and store the result for further work. MAX_FLAG_LEN and CHUNK_SIZE are equal to 16 and 4 
    • for chunk in range(0, MAX_FLAG_LEN, CHUNK_SIZE):
    piece0, piece1, piece2, piece3 = (beginner_flag[SHUFFLE_MASK[chunk + i]] for i in range(4))
    joined_chunk = Concat(piece3, piece2, piece1, piece0)
    add32_chunk = int.from_bytes(bytes(ADD32_VALUES[chunk:chunk + 4]), "little")
    add32_result = joined_chunk + BitVecVal(add32_chunk, 32)
  • This for loop will run 4 times exactly. One time for each 32-bit chunk.
    • The first line of the loop is a way of assigning four variables values in a single line, rather than having an expanded loop to do it, each piece will be assigned beginner_flag[SHUFFLE_MASK[chunk + i]]. The operation on the first iteration would look like piece0 = beginner_flag[SHUFFLE_MASK[0 + 0] –> piece0 = beginner_flag[0x02] –> piece0 = f2. This would be repeated 4 times each iteration of the loop, for a total of 16. The model/equation will be solving for f0-f15.
  • Next, we must get ready for the ADD32 operations those four pieces will be joined together by the Concat() function into a single 32-bit BitVec integer. joined_chunk will hold that shuffled and combined chunk.
  • Going off the example of the first iteration and following PEMDAS, ADD32_VALUES[0:0 + 4]) will grab four characters from our ADD32 values table, convert that 32-bit chunk to a little-endian bytes object, and then convert it from bytes into an integer. That result will get sored in add32_chunk.
  • The final line will finally add our shuffled bytes together. But first it must make sure both 32-bit chunks are BitVec datatypes using BitVecVal(). Now all that’s left is the XOR operation.

  • The following code shows us extracting each byte of a given chunk stored in add32_result and adding a rule to the solver that the specific byte XORed with the corresponding mask must be the same as the original value in beginner_flag. 
    • for i in range(4):
    potential_byte = Extract(8 * i + 7, 8 * i, add32_result)
    beginner_solver.add((potential_byte ^ XOR_MASK[chunk + i]) == beginner_flag[chunk + i])
    • On the first iteration: potential_byte = Extract(7, 0, add32_result).
    • Because chunk and i will correspond to each place in the flag, we can add the rule to solver that for each 8-bit char we extract and XOR, the char stored in beginner_flag[chunk + i] must match. This is the solution right here. The char put in must somehow survive the transformation. beginner_solver.add(potential_byte ^ XOR_MASK[0]) == beginner_flag[0], This also does the XOR without us actually having to carry out the operation ourselves. Instead, Z3 will do it as part of its rule set.

  • The following code appears after the previous for loop closes. 
    • def solver_builder():
    ...
    ...
    for i, ch in enumerate(b"CTF{"):
            beginner_solver.add(beginner_flag[i] == ch)
    beginner_solver.add(beginner_flag[15] == 0)
    
    for i in range(4, 14):
        beginner_solver.add(beginner_flag[i] >= 0x20, beginner_flag[i] <= 0x7e)
  
    return beginner_solver, beginner_flag
  • The first loop adds the known characters of CTF{ to the solver as rules. You could manually do this as four separate statements at the indexes of 0, 1, 2, and 3. Then, we add that the 15th character is equal to \0, which is the same as 0x00 or 0. This serves as adding known variables to a mathematical equation. Allowing systems of equations to help Z3 find the answer.
  • The second loop adds a rule that every single character in our flag must be within the printable ASCII range. A rule is added for every index from 4 to 14 because those are the characters we don’t already know.
  • Finally, we return the beginner_solver and beginner_flag that we configured.

  • The following code appears after the previous for loop closes. 
    • def main():
  beginner_solver, beginner_flag = solver_builder()
  while beginner_solver.check() == sat:
      beginner_model = beginner_solver.model()
      beginner_values = [beginner_model[f].as_long() for f in beginner_flag]
      print(bytes(beginner_values[:-1]).decode())
      beginner_solver.add(Or([f != v for f, v in zip(beginner_flag, beginner_values)]))
  • We call the solver_builder() function we built, configuring all the operations we did, adding rules to the Z3 solver, etc.
  • beginner_solver.check() is the command that checks for a solution to everything we set up. sat gets returned if a satisfiable solution has been reached. So, we keep running the solver, until all satisfiable solutions has been found and unsat is returned. Z3 will look for and find a mathematical solution or model that satisfies the equation we set up. Keep in mind, Z3 uses the term model differently than how it is used in math and physics. A model in Z3 means the set of specific values assigned to specific variables that causes the equation to evaluate as satisfiable.
  • When we call .model() we are retrieving the list of answers from the solver.
  • Because Z3 uses its own datatypes for variables, we have to retrieve them from the model and convert them into something python understands. So, for each item in beginner_flag f0-f15, we grab a value from our answer lookup table (beginner_model) at an incrementing index. Then, we convert what we pulled to an int. int used to be called long in older python versions. All these converted values get stored in beginner_values.
  • Next we print the solution in ASCII. To do this, we convert all the int values into bytes and then decode them into UTF-8 characters. The -1 is to ignore the null terminator at the end. Python doesn’t use null terminators like C does.
  • The last line’s aim is to make sure we can check to see if any other solutions exist. This helps us make sure that we have all the satisfiable characters. Z3 will give us the first satisfiable values it finds. So, we add a new rule to our solver using Or. first, our flag and values get zipped into a list of tuples ('f15', 0). Then for each f and v in each tuple, we assert that our flag character f{i} cannot be equal to the current value stored in the model: f15 != 0. This loop creates a series of conditions that culminate to mean that any value the solver found for our characters is no longer allowed to be the answer. This gets wrapped in a Z3 Or function. The Or function will evaluate as true if any single character in a new solution is not equal to the value in previous solutions. Then, the loop repeats. If mathematically there can be no other solutions that satisfy the newly added Or constraint, meaning no other possible values exist that can satisfy any of our f{i} characters, the .check() method will return unsat. Otherwise, other possible flags will get printed in succession.


Solve Script

  • from z3 import BitVec, BitVecVal, Concat, Extract, Solver, Or, sat
  
MAX_FLAG_LEN = 16
CHUNK_SIZE= 4
XOR_MASK = [0x76, 0x58, 0xb4, 0x49, 0x8d, 0x1a, 0x5f, 0x38, 0xd4, 0x23, 0xf8, 0x34, 0xeb, 0x86, 0xf9, 0xaa]
ADD32_VALUES = [0xef, 0xbe, 0xad, 0xde, 0xad, 0xde, 0xe1, 0xfe, 0x37, 0x13, 0x37, 0x13, 0x66, 0x74, 0x63, 0x67]
SHUFFLE_MASK = [0x02, 0x06, 0x07, 0x01, 0x05, 0x0b, 0x09, 0x0e, 0x03, 0x0f, 0x04, 0x08, 0x0a, 0x0c, 0x0d, 0x00]

def solver_builder():

    beginner_flag = [BitVec(f"f{i}", 8) for i in range(MAX_FLAG_LEN)]
    beginner_solver = Solver()

    for chunk in range(0, MAX_FLAG_LEN, CHUNK_SIZE):
        piece0, piece1, piece2, piece3 = (beginner_flag[SHUFFLE_MASK[chunk + i]] for i in range(4))
        joined_chunk = Concat(piece3, piece2, piece1, piece0)
        add32_chunk = int.from_bytes(bytes(ADD32_VALUES[chunk:chunk + 4]), "little")
        add32_result = joined_chunk + BitVecVal(add32_chunk, 32)
  
        for i in range(4):
            potential_byte = Extract(8 * i + 7, 8 * i, add32_result)
            beginner_solver.add((potential_byte ^ XOR_MASK[chunk + i]) == beginner_flag[chunk + i])
  
    for i, ch in enumerate(b"CTF{"):
        beginner_solver.add(beginner_flag[i] == ch)
    beginner_solver.add(beginner_flag[15] == 0)
  
    for i in range(4, 14):
        beginner_solver.add(beginner_flag[i] >= 0x20, beginner_flag[i] <= 0x7e)
  
    return beginner_solver, beginner_flag

def main():
    beginner_solver, beginner_flag = solver_builder()
    while beginner_solver.check() == sat:
        beginner_model = beginner_solver.model()
        beginner_values = [beginner_model[f].as_long() for f in beginner_flag]
        print(bytes(beginner_values[:-1]).decode())
        beginner_solver.add(Or([f != v for f, v in zip(beginner_flag, beginner_values)]))


if __name__ == "__main__": main()
